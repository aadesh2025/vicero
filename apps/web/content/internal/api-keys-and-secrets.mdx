## Customer API keys (`bf_`)

This is the explanation that used to be on the public docs page. It now lives only here: how
a workspace's server-to-server credentials work, so it can be given to a customer deliberately
rather than published to everyone.

Created under **Settings → API keys** (or `POST /v1/apikeys`). The key is shown **once** —
BotForge keeps only a hash and cannot show it again. Keys are prefixed `bf_` and either header
works:

```bash
curl https://YOUR_API_HOST/v1/agents -H 'X-API-Key: bf_live_xxx'
curl https://YOUR_API_HOST/v1/agents -H 'Authorization: Bearer bf_live_xxx'
```

A key resolves its own organization, so `X-Org-Id` is not sent with it.

| Scope | Can |
|---|---|
| `read` | Read everything the creator can read |
| `write` | Read and modify, but not publish or manage the organization |
| `admin` | Everything short of deleting the organization |

- **A key can never exceed the person who created it.** An `admin` scope minted by an `editor`
  behaves as an editor. Least privilege is enforced at creation, not at the call.
- **`admin` scope never means `owner`.** No key can delete an organization or transfer
  ownership, whoever created it.
- **Revoke** disables a key immediately and permanently; **delete** removes the record. Keys
  carry `last_used_at`, so check whether anyone still uses one before breaking it.
- Errors: `auth.invalid_api_key` means the key is unknown, revoked or expired. The management
  routes (`/v1/apikeys/*`) and the provider-credential routes (`/v1/credentials/*`) are in the
  [endpoint list](/vault/endpoints) and are deliberately absent from the public reference.

<Callout type="danger" title="Keys are bearer credentials">
Anyone holding the string can act as it. Keep them out of client-side code, out of git, and
out of URLs — a key in a query string ends up in logs and proxy caches.
</Callout>

## The one that will hurt you

**`SECRET_KEY` is not only a signing key.** `app/core/crypto.py` derives the Fernet
encryption key from `sha256(SECRET_KEY)`, and that key encrypts:

- every tenant's provider API keys (`provider_credentials.api_key_enc`), and
- every channel's tokens and secrets.

Rotating `SECRET_KEY` therefore does not merely invalidate sessions. It makes every stored
credential in the system undecryptable, for every tenant at once, with no error until
something tries to use one. Treat rotation as a migration with a re-encryption step, not as
a config change.

## Current state of this deployment

Only `GROQ_API_KEY` is set. Gemini, OpenAI, OpenRouter, Anthropic, every OAuth pair, every
channel credential, Stripe and Sentry are blank.

<Callout type="warn" title="An unkeyed provider is an outage, not a fallback">
Pointing an agent at a provider with no key configured does not degrade to a slower model.
Every turn fails with `llm.provider_unavailable`. Check before switching a client's agent.
</Callout>

## The `.env` formatting trap (ADR-044)

A comment must never share a line with an **empty** value:

```bash
GEMINI_API_KEY=            # get one at ai.google.dev   ← WRONG
```

The spaces after `=` are consumed as the separator, so `#` starts the value and the comment
text *becomes the key*. This shipped a placeholder to Google as a real API key once.

`KEY=value  # note` is fine. `config.py` defensively drops comment-only values and
`_warn_malformed_keys()` catches a value containing a space, tab or `#` — but **Compose's
`env_file` parser does neither**, so the trap is still live for anything Compose reads.

## Startup warnings

`_warn_missing_secrets()` in `app/main.py` logs loudly for a missing `GROQ_API_KEY` or
`N8N_API_KEY`, an insecure `SECRET_KEY` in prod, and malformed keys. `LLM_FORCE_FAKE` gets
an unmissable warning — and an `error` in prod — because a fake-forced process answers
every chat with `echo: <message>`, which reads exactly like a broken model rather than a
config choice. An hour was lost to that once.
