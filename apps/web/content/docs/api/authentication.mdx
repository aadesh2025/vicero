The BotForge REST API is served under `/v1`. Everything is JSON.

Requests act on behalf of a signed-in person, using a short-lived **session token**. Access for
servers and integrations is arranged by your workspace administrator.

## Session tokens

Signing in returns a short-lived **access token** and a long-lived **refresh token**:

```bash
curl -X POST https://YOUR_API_HOST/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"me@acme.com","password":"…"}'
```

```json
{ "access_token": "…", "refresh_token": "…", "user": { } }
```

Send the access token as `Authorization: Bearer <access_token>`. It expires after about
fifteen minutes; exchange the refresh token at `POST /v1/auth/refresh` for a new pair.

**Refresh tokens rotate.** Each exchange invalidates the one you used and issues a new one,
so a stolen refresh token is usable only until the legitimate client next refreshes — at
which point one of the two stops working and you have a signal that something is wrong.
Always store the token you get back.

### Choosing the organization

A person can belong to several organizations, so requests must say which one they mean:

```bash
curl https://YOUR_API_HOST/v1/agents \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "X-Org-Id: $ORG_ID"
```

Get the list from `GET /v1/orgs`. Omitting the header on an organization-scoped route is an
error, not a default.

## Other sign-in methods

Sign-up, OAuth with Google, GitHub or Facebook, magic links, password reset and email
verification are all available. They are rate-limited per source address.

## Public endpoints

The widget talks to `/v1/public/agents/{public_key}/…` with no token at all — the public
key in the path identifies one published agent's public chat and grants nothing else.
Channel webhooks are verified by signature rather than by token.

These are the only unauthenticated routes that touch your data, and both are rate-limited.
